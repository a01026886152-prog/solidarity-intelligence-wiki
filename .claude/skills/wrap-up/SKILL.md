# 정리해: 핸드오버 + 스킬·레슨 + 위키 배포

총비서 해일심이 하루 작업을 마칠 때 실행한다. 결과물은 네 가지다: **핸드오버**, **스킬 문서**(배운 기술이 있을 때), **레슨 문서**(배운 교훈이 있을 때), **위키 문서**. 모두 검수AI 랑랑별의 검수를 거친다. 사용자용 설명은 [`docs/wrap-up-command.md`](../../../docs/wrap-up-command.md)에 있다.

## 1단계. 오늘 한 일 모으기

아래를 모두 모은다. 기억에만 의존하지 않고 기록으로 확인한다.

1. 이 대화에서 사용자가 요청한 것, 해일심이 한 것, 사용자가 내린 결정과 그 이유
2. 오늘 커밋: `git log --since=midnight --oneline --all`
3. 아직 커밋하지 않은 변경: `git status --short`
4. 오늘 만든 결과물: `uijeong/outputs/` 아래 오늘 날짜 파일
5. 오늘 만든·합친 PR 번호와 주소 (대화와 커밋 메시지에서)
6. 직전 핸드오버(`docs/handover-*.md` 가운데 가장 최근 것)의 '남은 작업'. 오늘 끝낸 것과 아직 남은 것을 가른다.

## 2단계. 핸드오버 쓰기

`docs/handover-<주제>-YYYY-MM-DD.md`로 쓴다(주제는 소문자-하이픈 영문, 예: `uijeong`). 같은 날 같은 주제가 있으면 그 파일을 고쳐 쓴다. 구조는 [handover-template.md](handover-template.md)를 따른다.

- **다음 세션이 이 파일 하나만 읽고 바로 이어서 할 수 있어야 한다.** 어디에 무엇이 있는지(파일 경로, PR 주소, 사이트 주소), 무엇을 결정했는지, 다음에 무엇부터 할지 적는다.
- 사용자가 직접 해야 하는 일(계정 승인 요청, 결제, 설정 변경)은 따로 표시한다.
- **넣지 않는 것**: 비밀번호·토큰·API 키, 지원시스템 자료함 원문, 일반인 개인정보. 이 파일은 GitHub에 올라간다.
- 근거는 `CLAUDE.md`의 '근거 자료 표시'대로 커밋 해시·PR 주소·파일 경로를 단다.

## 3단계. 스킬과 레슨 정리

오늘 실제로 겪은 것만 쓴다. 없으면 만들지 않고 핸드오버에 "없음"이라고 적는다.

- **스킬**(다시 쓸 수 있는 기술·절차): 핸드오버의 '스킬' 절에 쓴다. 다른 작업에서도 쓸 만큼 크면 `docs/skill-<주제>.md`로 따로 쓴다(형식: [`docs/skill-supabase-auth-pitfalls.md`](../../../docs/skill-supabase-auth-pitfalls.md)).
- **레슨**(실수·판단에서 얻은 교훈): 핸드오버의 '레슨' 절에 쓴다. 크면 `docs/lesson-<주제>.md`로 따로 쓴다(형식: [`docs/lesson-supabase-integration.md`](../../../docs/lesson-supabase-integration.md)).
- 이미 같은 주제의 skill·lesson 문서가 있으면 새로 만들지 않고 그 문서에 덧붙인다.
- 스킬 문서(`.claude/skills/`)를 고쳐야 할 교훈이면, 고칠 내용을 핸드오버 '남은 작업'에 적고 사용자에게 고칠지 묻는다. 묻지 않고 스킬을 바꾸지 않는다.

## 4단계. 본인 위키에 배포

[`docs/wiki-publish-prompt.md`](../../../docs/wiki-publish-prompt.md)의 온톨로지 적용 규칙 1~8을 그대로 따라, 오늘 작업을 위키 문서 하나로 정리한다.

1. 분류: 개념 → `wiki/concepts/`, 현장 기록 → `wiki/field-notes/`, 도구·절차 사용법 → `wiki/how-to/`, 사례 분석 → `wiki/case-studies/`. 애매하면 사용자에게 묻는다.
2. `templates/`의 해당 템플릿을 따르고, 한 줄 요약·태그 3~5개·작성자·작성일을 채운다. 작성자는 `profile.md`의 이름 또는 사용자에게 물은 이름, 그리고 "총비서 해일심(Claude)"을 함께 적는다.
3. 같은 주제 문서가 이미 있으면 새로 만들지 않고 그 문서에 덧붙인다.
4. 관련 위키 문서 링크를 1개 이상 건다.
5. **공개해도 되는 내용만** 쓴다. 의원실 내부 판단, 자료함 원문, 개인정보는 빼고, 방법과 배운 점 위주로 쓴다.
6. 위키에 올릴 만한 내용이 없는 날이면 만들지 않고 이유를 알린다.

## 5단계. 검수

핸드오버, 위키 문서, 새로 만든 skill·lesson 문서를 랑랑별(`rangrang-byeol`)에게 넘겨 검수받고, `CLAUDE.md`의 '검수 절차'대로 고친다. 특히 커밋 해시·PR 번호·파일 경로가 실제와 맞는지, 비밀정보·자료함 원문이 없는지 확인받는다. 검수 보고서(`*.검수.md`)는 커밋하지 않는다.

## 6단계. 배포

1. 사용자에게 만든 파일 목록을 보여 주고, 커밋해서 올려도 되는지 묻는다.
2. 허락하면 `wrap-up/YYYY-MM-DD` 브랜치를 만들어 핸드오버·skill·lesson·위키 문서만 커밋하고(`git add`에 파일을 하나씩 지정한다. `uijeong/outputs/research/`, `*.검수.md`, `profile.md`는 넣지 않는다), `git push -u origin wrap-up/YYYY-MM-DD`로 올린다.
3. PR을 만든다. GitHub 도구가 없으면 PR 만들기 주소(`https://github.com/<저장소>/compare/master...wrap-up/YYYY-MM-DD`)를 알려 준다. 합치기(머지)는 사용자가 하라고 할 때만 한다.

## 7단계. 마무리 보고

사용자에게 짧게 알린다.

- 만든 파일과 PR 주소
- 랑랑별이 찾은 문제와 고친 것
- 다음에 이어서 할 때 첫 메시지 예시: `어제 핸드오버 읽고 이어서 하자`
- 사용자가 직접 해야 할 일
